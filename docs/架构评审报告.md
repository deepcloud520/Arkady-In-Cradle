## 一、总体判断

**这是一个"骨架远超平均水平、接缝处系统性失守"的项目。**

三个必须正视的结论：

1. **文档描述的是目标架构，代码实现的是另一个东西，而两者之间的差距没有被任何自动化机制守住。**
   这不是零散的文档过期，而是系统性的：AGENTS.md 声称的 `scipy.ndimage.label` + `skimage.find_contours` 体素化、QThread 后台烘焙 + 双缓冲热交换、`h5py` 存档、`Simulation.get_state()`、YAML/Pydantic 数据驱动、A* < 1ms —— **全部在代码中不存在或未接线**。而测试全绿，因为测试测的是"已实现的那部分"。

2. **几处最严重的缺陷不在算法，而在"接线"**：精心写的内核（三轴 Slab 碰撞、A-T 两段式穿甲）被一个不按 `guid_law` 过滤的调用点毁掉，而这条路径**同时被军械库的每个单元测试放过**。这比"算法写错"危险得多——算法错会被单测抓住，接线错只会被集成测试抓住，而集成测试只断言"事件计数 > 0"。

3. **性能声明与实测相差 3 个数量级。** `docs/指挥官指南.md` §七自曝 AI 决策目标 <1ms / 实测 ~570ms；我实跑 `benchmark_phase6` 得到 **788ms**（AI）/ **553ms**（伤害池）/ **1802ms**（整体吞吐）。一个 1 秒 tick 预算被单帧 AI 吃掉 79%，而 `benchmark_phase6.py` 只 `print` 不断言 —— CI 永远守不住这个目标。

**同时必须说清楚：这个项目的工程质量在同类个人项目里属于上游。** SoA 池 + Numba 内核的纪律执行得很干净（74 处 `@njit(cache=True)`，热路径无 Python 对象）、依赖注入骨架完整、`lulilo` 对 UI 技术栈零渗透（`PySide6|moderngl|glm` 在引擎内零命中）、GL/Qt 的历史陷阱修复全部还在代码里且配有针对性回归测试、大量技术决策在注释里记录了**失败方案和失败原因**。问题不是"不会写"，而是"缺一个守门人"。

## 三、总体设计：结构性问题（架构级，非 bug）

### 3.1 「叙事优先」是产品定位，但叙事层在生产路径上被关断

`ui/main_window.py:132` 第一行就是 `return  # 暂不加载 story/ 对话树`，后面 8 行加载逻辑成为**不可达死代码**。而资产齐全：`story/dialogues/{prologue,first_blood}.yaml` + `story/triggers/chapter1.yaml`，schema 与 Pydantic 模型吻合。

更严重的是 📋 `ChoiceOptionConfig.condition`（`dialogue.py:42`）**被完全忽略**——`_enter` 只取 `o.text`（`:273-274`），`advance` 不校验（`:212-221`），于是 `prologue.yaml:42` 的条件选项永远可见可点。而 `tests/test_narrative.py:195-203` 的测试名与 docstring 声称"只有满足条件才显示"，断言却是"骨架期：条件选项始终列出"—— **测试以相反断言固化了 bug**。

> 产品定位是"战斗可跳过，剧情永远在场"。当前状态是"剧情根本不在场"。

### 3.2 时间模型是名义上的多分辨率

`loop.py:202-215` 只有**单级累加器**，无追赶循环、无 dt 上限、无最小/最大稳定 dt 契约。后果：

- `run_headless` 默认 `dt=1.0`（`loop.py:220`），此时 `combat`（0.01s）也每帧只跑一次 → 子弹精度**完全靠 `FiringControl` 内部子步**（`engagement.py:998-1004`）兜住，不在调度层。
- GUI 按 `step(1/60)` 驱动（`main_window.py:342`）→ `air_movement`（0.1s）每 6 帧才触发一次，但**dt 是 0.1 还是累计值取决于调用方**。

**这不是性能问题，是架构脆弱性**：物理正确性寄生于某一个子系统的内部实现。新增任何 `interval < 帧步长` 的子系统，都会**静默**拿到粗 dt。

### 3.3 「绝不阻塞主线程」缺少承载物

AGENTS.md 3.3 承诺"爆炸 → 后台 QThread 烘焙 → 双缓冲热交换，绝不阻塞主线程"。实际：

- ✅ **已复核**：`GraphPathfinder.set_graph()`（`pathfinding.py:114-116`，docstring 明写"双缓冲热交换后调用"）**零生产调用** —— 运行中的 A* 永远持有加载期快照，地形破坏对寻路永久无效。
- 📋 **子代理报告**：整个 `navmesh/` 包（`_baker` + `_tiles`）生产调用点为 0，唯一调用者是 `tests/integration_heightfield.py:49-58`；真实路径是 `remove_span → TerrainMap.invalidate_geometry() → 主线程同步全量重建`（`map.py:98-110`）。
- 📋 因此「炸桥断补给线」「弹坑绕行」在导航层不成立 —— 「自由破坏」是半闭环。

### 3.4 Phase 8「封印上帝视角」在生产路径上完全没有生效

> ✅ **已复核**：`TwinPool` / `TwinEngine` / `DataLinkNetwork` 在全仓**只被测试引用**（89 处匹配中生产代码为零）。

- `FormationAI.__init__(contact_provider=None)`（`ai.py:553/566`），无 provider 时走 `_default_contacts()` 直读敌方 `armor.pos`（`ai.py:660-676`，docstring 自陈"全知模型"）。
- 装配侧 `scenario.py:209-213` 与真实游戏场景 `world1.py:175` **都未注入** `contact_provider`，也**都没有创建** `TwinPool`/`TwinEngine`。

- 📋 即便换源，执行/瞄准仍读真值：`_in_range`（`ai.py:974-978`）、`_move_toward_target`（`:1005-1008`）、`_nearest_enemy`（`:1135-1159`，注释自陈"全知"）、射界规避（`:1055-1129`）；且 `fire()` 无 `confidence` 参数（`fire_air` 有，`:673-675`）→ **迷雾影响"打谁"，几乎不影响"打得准不准"**。

### 3.6 数据驱动承诺未落地

AGENTS.md 4.4「配置加载：YAML → Pydantic」、§十.4 YAML 数据驱动设计、`Reference/Global Weapons Systems.csv` —— 实际全部武器/弹药是 **Python 字面量硬编码**（`weapons.py:375-522` + `world1.py:39-113`，共 6 武器/8 弹药），`WeaponRegistry.from_yaml`（`:359-368`）零调用，项目根**无 `data/` 目录**，`Global Weapons Systems.csv` 从未被任何代码解析（全库唯一提及是 AGENTS.md:685）。

项目有 15k 行测试、695 个通过用例，但**没有 CI、没有性能回归门禁、没有文档-实现一致性检查**：

- `pytest-basetemp` 之类的回归靠人工跑。

- **`.github/` 下只有 `agents/erty.agent.md`，没有任何 workflow。**

这是本报告所有问题的**共同母因**：不是能力问题，是缺少"事实校验"的工程环节。

## 四、技术设计：已复核的严重缺陷

> 以下 8 项均由主评审人亲自读代码/运行命令确认（✅）。

### 4.1 🔴 制导内核不按 `guid_law` 过滤 → 普通子弹被双重积分 + 被导向原点

**这是本次评审发现的最严重缺陷。** 证据链：

1. 内核签名**没有 `guid_law` 参数**（`integrate.py:757-776`），循环只判 `active`：
   ```python
   for i in prange(m):
       if not active[i]: continue
       stage = int(guid_stage[i])
   ```
2. `guid_stage` 数组默认 `np.zeros(...)` = **0**（`pools.py:832`），而 `_GUIDANCE_STAGE_TRACK = 0`（`integrate.py:747`）—— **默认不是 BALLISTIC 而是 TRACK**。
3. 开火时制导字段只在 `if law_id:` 内设置（`engagement.py:544`）→ **无制导弹的 `guid_stage` 永远是默认 0 = TRACK**，`guid_track_fov_cos` 默认 1.0 → FOV 门限 `if fov_cos < 1.0` **不生效**。
4. 调用点把**整池数组**传给内核，每个 law 各一次（`engagement.py:1086-1100`），随后**再无条件**调用一次直线积分（`:1102`）。

**后果**：只要空中有任一制导弹（AAM/SAL/末敏弹），所有在飞的普通子弹会：
- 被 `control_fn` 以 `guid_target_pos=(0,0,0)` 为导向目标**转向世界原点**；
- 被制导内核积分一次、又被直线积分一次 → **位置与重力双算**；
- 多律同时存在时（`world1` 确有 `dual_pulse_pn` + `glide_bomb`）每个律各积分一次；
- `_stop_guidance`（`:2000-2002`）只置 `guid_law=-1`，而内核不看该字段 → **停导无效**。

**为什么测试全绿**：纯弹道单测场景中 `law_ids` 为空 → 不触发；制导单测场景中只有制导弹。这个 bug 只在"子弹与导弹同时在空中"时显现，而**没有任何测试断言过同场景混合弹药**。

⚠️ 动态影响幅度未量化（本环境无法逐发测量命中率），但代码路径本身确凿。

### 4.2 🔴 碰撞空间哈希索引只建一次、永不失效

```python
if not self._built:                      # collision.py:553-554
    self.build_index(...)
```
`self._built = True` 后（`:530`）**只有 `clear()`（`:589`）才复位**，而 ✅ 全仓核对：`detector.clear()` **零生产调用**（`damage_submission` 池的 `clear()` 是另一回事）。

**后果**：索引按"装甲建索引那一刻的位置"固定。之后任何单位移动超过一个网格（默认 50m）或**在索引建立后才 spawn** 的单位，都永久脱离候选集 → **静默不命中**。对照同项目 `FormationResolver.resolve` 每次重建（`:794-799`）—— 同一个文件里两种做法。

### 4.3 🔴 `ArmorPool._expand` 漏 resize `vel` → Numba 无检查越界

✅ 核对 `pools.py:335-373`：`_expand` resize 了 pos/half/yaw/hull_idx/parts_destroyed/active/wp/wp_count/wp_idx/mesh_id/pitch/roll/suspension/contact_z/contact_mesh_id/pitch_vel/roll_vel/rcs/ecm/side/role/order/target_idx/target_kind/comm/contact_age/formation_id —— **唯独漏了 `vel`**（定义于 `:169`）。

对照：`ProjectilePool` 在 `:979` resize 了 vel，`AircraftPool` 在 `:1563` 也 resize 了。**只有 ArmorPool 漏了。**

**后果**：`ArmorPool` 扩容到 4096（`test_entities.py:148` 证实会扩到 4096）后，`armor.vel` 仍是 `(2048,3)`。`integrate_armor_movement_*` 会写 `vel`（2026-08-18 新增的直射前置量功能依赖它）→ **Numba 核内无越界检查 → 静默错误读数或静默内存破坏**。

### 4.4 🔴 hook 异常 = 模拟时钟冻结 + dt 螺旋放大

`loop.py:196-218` 的调度循环**无 try/except**（对比 `:163-168` 只保护了 `command_handler`），且累加器清零写在 hook 调用**之后**：

```python
acc = self._rate_accum[name] + dt
if acc >= interval:
    hook(self, acc)          # ← 抛异常则下一行不执行
    self._rate_accum[name] = 0.0   # ← 已累加值保留
```

**后果**：某 hook 抛异常 → 后续 hook 全跳过、`state.sim_time`/`tick_count` 不推进（`:217-218` 不可达）→ **模拟时钟冻结、墙钟继续**；且失败 hook 保留累加值，下帧 dt 更大 → 配合 `engagement.py:999` 的无界 `while` → **越崩越贵的崩溃循环**。

对"战斗可跳过、剧情永远在场"的产品定位，这是最坏失效模式：战斗崩 → `sim_time` 冻结 → 剧情触发条件永不满足。

### 4.5 🔴 `ArtilleryAI` 无阵营过滤地消费共享事件总线

✅ 复核 `ai.py:1480-1488`：`for e in self.events.drain_filter({"support_request"})` —— 逐条处理，**只判 `kind == "artillery"`，不判阵营**；而请求体（`ai.py:764-772`）**没有 side 字段**；`scenario.py:196-207` 为每阵营各建一个 `ArtilleryAI` 并共享同一 bus。

**后果**：先 tick 的炮兵吞掉**全部** `support_request`（含敌方的），并按敌方给的坐标朝友军阵地开火 —— **跨阵营指挥链泄漏**。

### 4.6 🟠 引擎内部反向依赖：`combat → simulation`

✅ `combat/engagement.py:113`：`from Airia.lulilo.simulation.loop import EventBus, TICK_BULLET`

违反 AGENTS.md 4.1 单向链 `combat → logistics → simulation`。当前**不构成硬循环**（`loop.py:22-24` 不回指 combat），但副作用是：任何 `import combat.engagement` 都会触发 `simulation/__init__.py` 全包初始化（连带 msgpack 序列化）；且一旦 `loop.py` 未来 import 任何 combat 成员，立刻变硬循环。

### 4.7 🟠 UI 直读活体 SoA，绕过唯一接缝

✅ `main_window.py:346-349`：`snapshot = self.simulation.state.snapshot()` → `armor = snapshot.pools.get("armor")` → `armor.pos` 做速度差分。

`state.py:9` 明言快照是**浅视图**（"直接引用 SoA 数组…只读语义由约定保证"）→ 这里拿到的是**活体数组**。正面违反 `docs/phase5-ui-pipeline-design.md:348`「绝不直接访问 `SimulationSnapshot.pools` 或 SoA 数组」，而该文档 :877 又把这条验收打了 ✅。

### 4.8 🔴 装甲类型 `armor_type` 从未接线 → 全场恒按 RHA 结算

✅ **已复核三方证据链**：

1. `world1.py:260` 设 `armor_type=int(ArmorType.COMPOSITE)`、`:268` 设 `REACTIVE` —— 场景**确实配置了**装甲类型。
2. 但 `set_unit_config`（`engagement.py:361-363`）**只做 `self._configs[armor_idx] = cfg`，不转发**给伤害结算器。
3. 伤害侧 `armor_type_of`（`damage.py:498-499`）默认返回 `RHA`，只有 `set_armor_type`（`:494-496`）能改 —— 而该函数**全仓仅 tests 调用**（`grep` 确认生产零调用）。

**后果**：`ARMOR_EFFECTIVENESS` 的关键一行（COMPOSITE 对 HEAT **×2.5**，`damage.py:64`）与 `TARGET_ARMOR_MODEL` 的复合/反应/间隙装甲行为**全部是死代码**。场景里宣称的"复合装甲 M1A2 vs 反应装甲 T-14"在穿深计算上**完全没有区别** —— 复合装甲的抗破甲优势不存在，反应装甲不爆炸。

这是"配置写了、装配忘了"的典型：**每一层单测都过，因为单测各自直接调 `set_armor_type`**。

### 4.9 🟠 制导律 PN 方向偏差 90°

📋 `guidance.py:104-110` 输出的 `a = N·max(Vc,0)·λ̇` 中，`λ̇` 是**视线旋转轴**（垂直于交战平面），而标准矢量比例导引需要**面内侧向**指令 `N·Vc·(ω × v̂_m)`。

子代理给出的验算：共面水平交战 `r=(0,R,0)`、`v_m=(V,0,0)`、静止目标时，`ω=(0,0,V/R)` —— 实现给出 `a ∥ +z`（**出平面**），标准应给 `a = +y`（朝向目标一侧）。

量级一致、方向差 90°，实际仍能命中是因为靠交叉耦合间接收敛。**而文档 `phase6-guidance-pipeline.md:1094-1096` 把这个现象当成正常行为记录，测试也只断言"三维距离收敛"** —— 又一次是"文档与测试共同掩盖"的模式（同 §4.1）。

### 4.10 🟠 地图尺寸相关常量仍是隐患（15km"修复"未真正修复）

✅ 复核 `world1.py:173`：`CollisionDetector(world_half=8000.0)` → 网格覆盖 `[-8000, 8000)²`，而地图是 `[0, 15000]²`（`gl_widget.py:52-54`，400 格 × 37.5m）。

📋 `world1.py:331` 的 `_squad(9350, 9350, ..., count=16)` —— **16 辆北约坦克的坐标超出网格覆盖范围**，`collision.py:271` 越界即跳过登记 → 这些车既不可被命中、也不参与编队推开。

`dev-progress.md:127` 记录"15km 修复 = 传入 world_half=8000"并自述"不改管线"，实际只是把战场收拢到中心**掩盖**了问题，而非修正网格覆盖策略。正确做法是**由地图实际 AABB 推导网格范围**（`grid_min=min_corner`、`counts=ceil(extent/grid_size)`），不假设中心对称。

### 4.11 🟠 读档契约定型冲突 + AI 状态不入档
